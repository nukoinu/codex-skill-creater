# Create a repository-local Workflow Skill

Use this Skill to create a Workflow Skill: it owns orchestration between capabilities—phase order, routing, handoffs, transitions, and stop boundaries. Component Skills own their domain behavior and detailed procedures. Do not use this Skill to create a component Skill, run Agents or sessions, or build an engine, DSL, registry, router, harness, or automatic capability creator.

1. Establish the requested outcome, trigger and activation boundary, production or explicitly requested evaluation-only role, expected artifact, component capabilities, material risks, and exclusions. Inspect only applicable `AGENTS.md`, native Skill conventions, existing same/overlapping Workflow Skills, and candidate component Skills needed for that workflow.
2. Before a workflow edge names, invokes, links to, or tells the user to read an existing Skill, inspect that target's entry contract: name, description, use conditions, exclusions, high-level responsibility, and only the entry guidance needed for this edge. Route only when the exact phase condition is compatible. Do not infer compatibility from proximity, shared history, terminology, or useful facts; read deeper references only to resolve a concrete routing or handoff ambiguity.
3. Write the smallest native Workflow Skill. For every material phase make its purpose, entry, required input, responsible capability, expected output, exit, handoff, conditional continuation, and stop/error behavior explicit where applicable. Keep the form natural-language-first; simple phases need not use a mechanical schema. Derive approval, validation, authority reacquisition, fixed-input, and same/fresh-instance semantics from target-repository authority and component contracts—never from a template assumption.
4. Keep component procedures with their component Skills. Preserve material handoff ownership: artifact or value, fixed authority versus advisory context, permitted modification or reinterpretation, authority the next phase must reacquire, and missing/ambiguous-handoff stop behavior. Use a concise `SKILL.md`, add `references/workflow.md` only when detailed orchestration needs it, and add an explicit self-improvement path from version one. Do not create speculative files or directories.
5. If an edge is invalid or a capability is absent, first use direct repository authority when sufficient, then another compatible component, then narrow workflow-local orchestration only when it is genuinely workflow-owned; otherwise report the missing capability or ownership conflict and stop that path. Never widen a neighboring Skill or auto-create the missing capability. A separate explicit request may use `$skill-create` for that component.
6. Create a same-purpose alternative only for an explicit evaluation/shadow/historical-comparison request. Give it a distinct name and an evaluation-only description and body that prohibit normal implicit production routing; inspect the production Workflow Skill as evidence without copying it mechanically, leave it unchanged, and require later explicit promotion or replacement. Do not add routing metadata, a resolver, or comparison infrastructure.
7. Report the created files, invocation, discovery and routing decisions, phase/handoff and stop semantics, knowledge placement, validation, missing capabilities, and any material overlap or authority conflict. Normal creation never mutates this Skill. Read [the creation guide](references/creation-guide.md) when designing the generated Workflow Skill. Read [self-improvement guidance](references/self-improvement.md) only after an explicit request to improve, refine, evolve, review for improvement, or update `workflow-skill-create` itself.
